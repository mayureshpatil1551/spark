## Section 1: PySpark & Spark Core

### 1. Walk me through Spark's architecture — driver, executors, cluster manager.
**Short:** The driver plans the job and creates the DAG, the cluster manager allocates resources, and executors run the actual tasks in parallel on worker nodes.
**Detailed:** "In my day-to-day work on Azure Databricks, when I submit a PySpark job, the driver program runs on the cluster's driver node — it builds the logical plan, converts it into a DAG of stages and tasks, and negotiates resources with the cluster manager. In my case that's Databricks' own cluster manager sitting on Azure VMs. The actual work — reading files, transforming, writing — happens on executors, which are JVM processes on worker nodes, each running tasks in parallel across partitions of the data. For my FinOps pipelines processing 26+ TB, this parallelism across executors is exactly what let us process that volume within our SLA windows."

### 2. Difference between transformations and actions in Spark.
**Short:** Transformations are lazy — they build a plan but don't execute, like `filter` or `withColumn`. Actions trigger execution, like `count` or `write`.
**Detailed:** "Transformations like `select`, `filter`, `join`, or `withColumn` just add steps to Spark's logical plan — nothing runs yet. It's only when I call an action — `write`, `count`, `collect` — that Spark actually optimizes and executes the whole chain. In my eCDP pipelines, I'd chain multiple transformations for cleansing and dedup logic, and only trigger execution once at the final `write` to Iceberg tables — this let Spark's Catalyst optimizer combine and reorder operations for better performance instead of executing each step eagerly."

### 3. What is lazy evaluation and why does it matter?
**Short:** Spark doesn't execute transformations immediately — it builds a DAG and optimizes the whole chain before running, which reduces unnecessary computation and I/O.
**Detailed:** "Lazy evaluation means Spark waits until an action is called before doing any real work. The benefit is optimization — Spark's Catalyst optimizer can look at my entire chain of transformations and reorder or combine them, like pushing filters down before joins to reduce data shuffled. In practice, on my financial data pipelines, this meant I could write clean, readable transformation logic step by step without worrying about performance, because Spark handles the physical execution plan for me."

### 4. How do you handle data skew?
**Short:** I identify skewed keys using Spark UI task duration, then use salting, broadcast joins for small tables, or repartitioning to balance the load.
**Detailed:** "I've run into skew mainly during joins on financial account IDs where a few keys had disproportionately more records. First, I check the Spark UI — if one or two tasks take much longer than others, that's a sign of skew. My go-to fixes: if one side of the join is small, I use a broadcast join to avoid the shuffle entirely. If both sides are large and skewed, I salt the skewed key — add a random suffix to spread records across more partitions, then aggregate back. I also use `repartition()` on the skewed column when it's a straightforward data distribution problem rather than a join skew."

### 5. repartition() vs coalesce()
**Short:** `repartition()` does a full shuffle and can increase or decrease partitions; `coalesce()` avoids a shuffle but can only decrease partitions.
**Detailed:** "I use `repartition()` when I need to increase parallelism or fix skewed partitions — it does a full shuffle, which is expensive but gives even distribution. `coalesce()` I use when writing final output — say after aggregations, if I want to reduce from 200 partitions down to fewer output files without an expensive shuffle, coalesce merges partitions on the same node. In my pipelines, I'd typically repartition before a heavy join, then coalesce before the final write to avoid generating hundreds of small files in ADLS Gen2."

### 6. Narrow vs wide transformations.
**Short:** Narrow transformations like `map` or `filter` don't require shuffling data across partitions; wide transformations like `groupBy` or `join` do.
**Detailed:** "Narrow transformations operate within a single partition — no data movement needed, so they're cheap. Wide transformations like `groupBy`, `join`, or `distinct` require shuffling data across the network so related keys end up on the same partition, which is expensive. When I'm designing a pipeline, I try to push narrow transformations — filtering, column derivations — as early as possible to reduce the volume of data going into an expensive wide transformation like a join, which directly cut execution time in my incremental load pipelines."

### 7. How do you tune executor memory and cores for a large job?
**Short:** I balance executor memory, cores per executor, and number of executors based on data volume and cluster size, avoiding too few large executors or too many tiny ones.
**Detailed:** "For a 26+ TB migration, I didn't just crank up cluster size — I tuned based on the workload. I typically avoid extremely large executors, since bigger heaps mean longer GC pauses; I aim for a sweet spot like 4-5 cores per executor and size memory so I don't hit spill-to-disk on shuffles. I also monitor the Spark UI — Storage tab for cache usage, and stage details for shuffle read/write size — and adjust `spark.sql.shuffle.partitions` since the default 200 is often wrong for very large or very small datasets. For the FinOps migration, tuning this along with Z-ordering was a big part of how we hit our latency targets."

### 8. Explain broadcast joins.
**Short:** Broadcast joins send a small table's full copy to every executor, avoiding a shuffle join — used when one side of the join is small enough to fit in memory.
**Detailed:** "When I'm joining a large fact table with a small dimension or lookup table — say a currency code or business unit mapping table in FinOps — I use a broadcast join. Spark copies that small table to every executor, so the join happens locally without shuffling the large table across the network. Spark auto-broadcasts tables under a size threshold, default 10MB, but I've explicitly used `broadcast()` hints when I know a table is small but Spark's stats say otherwise, especially after multiple transformations where size estimates get stale."

### 9. How would you debug a slow Spark job?
**Short:** I start with the Spark UI — check for skewed stages, excessive shuffle, spill to disk, or too many small tasks — then narrow down to the specific transformation causing it.
**Detailed:** "My process: first I open the Spark UI and look at the Stages tab to find which stage is taking disproportionately long. I check for shuffle read/write sizes — if they're huge, that points to a wide transformation like a join or groupBy that needs optimization. I also check for data skew — one task taking much longer than others in the same stage. Sometimes it's not compute at all — it's too many small files causing overhead, which I've dealt with using compaction in our Delta/Iceberg tables. In one case in eCDP, I traced a slow pipeline to a non-partition-pruned filter, fixed it by aligning the filter to our partition column, and that was part of how we cut a pipeline from 4 hours to 58 minutes."

### 10. RDD vs DataFrame vs Dataset — why DataFrames?
**Short:** RDDs are low-level with no schema or optimization; DataFrames have schema and use Catalyst/Tungsten for optimization; Datasets add type-safety, mainly in Scala/Java.
**Detailed:** "I work almost entirely with DataFrames because they give schema awareness, and Spark's Catalyst optimizer can generate an efficient physical execution plan automatically — something RDDs don't get since they're unstructured, low-level. Datasets add compile-time type safety, but that's more relevant in Scala; in PySpark, DataFrames are effectively the standard. For my cleansing and transformation logic in FinOps and eCDP, DataFrames also let me write concise, SQL-like operations, which matters when I'm building config-driven, reusable transformation frameworks."

### 11. How do you handle schema evolution?
**Short:** I use Iceberg/Delta's built-in schema evolution support — adding columns without rewriting the table — combined with schema validation checks at ingestion.
**Detailed:** "In pharmaceutical MDM, source systems change fairly often, so schema evolution was a real concern. Apache Iceberg handles this natively — I could add, rename, or reorder columns without rewriting the whole table, since it tracks schema by field ID, not position. On the ingestion side, I built validation checks that compare incoming schema against expected schema and flag or route unexpected new fields rather than silently failing or dropping data, which matters a lot in a regulated pharma environment."

### 12. persist() vs cache() — when have you used them?
**Short:** `cache()` stores data in memory only using default storage level; `persist()` lets you choose the storage level, like memory-and-disk, for larger datasets.
**Detailed:** "I use `cache()` for smaller intermediate DataFrames I reuse multiple times in a job — like a cleaned reference table I join against several times. For larger datasets that don't fit fully in memory, I use `persist(StorageLevel.MEMORY_AND_DISK)` so Spark spills to disk instead of recomputing from scratch. In my Golden Record identity resolution logic, I'd cache the deduplicated reference dataset since I referenced it across several transformation steps, which avoided redundant computation."

## Section 2: Spark SQL, Iceberg & Delta Lake

### 13. Iceberg vs Delta Lake — why did eCDP use Iceberg and FinOps use Delta?
**Short:** Both are open table formats with ACID transactions, but Iceberg has stronger partition evolution and multi-engine support, which fit eCDP's S3 + Snowflake dual-target setup; Delta integrates tightly with Databricks, which fit FinOps's Azure-native stack.
**Detailed:** "eCDP needed to write to both Iceberg and Snowflake simultaneously for our dual-target migration, and Iceberg's format is engine-agnostic — Snowflake, Spark, Athena can all read it without vendor lock-in. It also handles partition evolution better; I could change partitioning strategy without rewriting historical data, useful as our pharma datasets grew. FinOps, on the other hand, was fully Azure-native with Databricks as the primary compute, so Delta Lake made more sense — it's tightly integrated with Databricks' optimizations like auto-compaction, and our downstream consumption was mainly through Databricks SQL and Azure SQL, not multi-engine."

### 14. Explain Iceberg's hidden partitioning.
**Short:** Iceberg tracks partition transforms internally, so you can query by the actual column, like a date, without needing to know or specify the physical partition layout.
**Detailed:** "In Hive-style partitioning, you'd have to know the physical partition column, like `year=2025/month=03`, and explicitly filter on it, or Spark won't prune partitions. Iceberg abstracts this — you define a partition transform, say `days(order_date)`, and Iceberg tracks the mapping internally. So when I filter on `order_date` directly, Iceberg automatically prunes the right files without me needing to know the underlying partition structure. This was useful in eCDP because it meant downstream users querying pharma data didn't need to understand our physical layout to get partition pruning benefits."

### 15. How does Iceberg handle schema evolution without rewriting the table?
**Short:** Iceberg tracks columns by unique field IDs rather than position, so adding, dropping, or renaming columns is a metadata-only operation.
**Detailed:** "Because Iceberg assigns a permanent field ID to each column instead of relying on ordinal position like Hive does, schema changes — adding a new column, renaming, or even reordering — are pure metadata operations. The underlying data files don't need to be rewritten. This mattered a lot in our pharma MDM project because source systems would periodically add new fields, and I could evolve the target schema safely without a costly full-table rewrite or downtime."

### 16. What is time travel and have you used it?
**Short:** Time travel lets you query a table as it existed at a previous snapshot or timestamp — I've used it for auditing and validating data before/after a transformation.
**Detailed:** "Both Iceberg and Delta keep a version history of snapshots. I used this in FinOps mainly for debugging and validation — if a downstream report looked wrong, I could query the table as of an earlier snapshot to compare and pinpoint exactly which load introduced the issue. It's also valuable in a regulated environment for audit trails — being able to show what the data looked like at a specific point in time for compliance purposes."

### 17. How does Iceberg manage snapshots, and how would you roll back a bad write?
**Short:** Every write creates a new immutable snapshot; to roll back, I'd use Iceberg's rollback or `set current-snapshot-id` procedure to point the table back to a known-good snapshot.
**Detailed:** "Each write operation in Iceberg — insert, update, delete — creates a new snapshot rather than mutating existing files, so previous snapshots stay intact and queryable. If a bad load happened — say a job wrote duplicate or corrupted records — I'd first identify the last good snapshot ID from the table history, then use Iceberg's rollback procedure to reset the table's current pointer back to that snapshot. This is much safer than trying to manually delete and reload data, and it's something I've relied on as a safety net during our large-scale pharma migration."

### 18. What is Z-Ordering and how did it help cut query latency by 40%?
**Short:** Z-Ordering co-locates related data based on specified columns, so queries filtering on those columns read far fewer files — I applied it on frequently filtered columns in our reporting layer, which drove the 40% latency cut.
**Detailed:** "Z-Ordering is a multi-dimensional clustering technique — it physically sorts data files so that rows with similar values across specified columns end up co-located. I applied it on the columns our 300+ business reports filtered on most — things like business unit and reporting period. Without Z-ordering, a filtered query might scan many files unnecessarily; with it, Spark's data skipping could eliminate most files upfront based on min/max statistics. Combined with partition tuning and file compaction, this Z-ordering strategy was the core driver behind cutting query latency by 40% across our finance reporting workloads."

### 19. How do you handle the small file problem?
**Short:** I use scheduled compaction jobs — `OPTIMIZE` in Delta or Iceberg's rewrite data files procedure — to merge small files into larger, right-sized files, and I tune batch/micro-batch sizes upstream to avoid generating them in the first place.
**Detailed:** "Small files are a common side effect of frequent incremental writes — each micro-batch or incremental load can create many small files, which hurts read performance because of the overhead of opening many files. My approach was two-fold: reactively, I ran periodic compaction — `OPTIMIZE` on Delta tables, or Iceberg's `rewrite_data_files` — to consolidate small files into fewer, larger ones. Proactively, I tuned how our incremental loads batched writes, so we weren't creating excessive tiny files in the first place. This was part of the file compaction work that contributed to our latency improvements in FinOps."

### 20. Explain Medallion architecture and how you implemented it across two projects.
**Short:** Bronze holds raw ingested data, Silver holds cleaned/validated data, Gold holds business-ready aggregated data — I implemented this in both FinOps (Delta) and eCDP, though eCDP used Raw/Trusted/Curated naming instead of Bronze/Silver/Gold.
**Detailed:** "In FinOps, Bronze was the raw landing zone for Oracle and flat-file extracts straight from ADF, untouched. Silver applied cleansing, deduplication, standardization, and business rules using PySpark — this is where most of my transformation logic lived. Gold was the curated layer loaded into Azure SQL and Delta tables optimized for the 300+ downstream business reports. In eCDP, we used the same conceptual layering but named it Raw, Trusted, and Curated to align with the pharma platform's terminology — Raw was direct ingestion from Oracle, Snowflake, REST APIs and Smartsheets; Trusted applied validation and Golden Record identity resolution; Curated fed the final reporting and regulatory layer."

### 21. How do you enforce data quality checks between layers?
**Short:** I build validation checks — null checks, schema checks, referential integrity, and row-count reconciliation — as gates between each layer, and route failing records to a quarantine path.
**Detailed:** "Between Bronze/Raw and Silver/Trusted, I run schema validation and null/completeness checks on critical business fields — if source data breaks contract, I flag or quarantine those records rather than let them silently corrupt downstream reports. Between Silver and Gold, I run reconciliation checks — row counts, key business metric totals — to make sure transformations didn't unintentionally drop or duplicate records. In eCDP specifically, since we were doing Golden Record identity resolution, I validated that duplicate/conflicting records were properly resolved before promoting to the Curated layer, which was critical since this fed regulatory reporting."

### 22. Difference between data lake, data warehouse, and data lakehouse.
**Short:** A data lake stores raw, schema-on-read data cheaply at scale; a data warehouse stores structured, schema-on-write data optimized for fast BI queries; a lakehouse combines both — lake-style storage with warehouse-style ACID transactions and performance.
**Detailed:** "A data lake, like our ADLS Gen2 Bronze layer, stores raw data in its native format cheaply and at scale, but querying it directly isn't optimized. A data warehouse, like Azure SQL Database in FinOps, stores structured, curated data with strong query performance for BI, but it's expensive to scale and less flexible for raw/semi-structured data. A Lakehouse — which is what I built with Delta Lake and Iceberg — gives you the low-cost scalable storage of a lake, but adds ACID transactions, schema enforcement, and performance features like Z-ordering, so you get warehouse-like reliability and speed directly on lake storage, without needing to duplicate data into a separate warehouse for every use case."

## Section 3: Kafka & Real-Time Streaming (Learned Through Self-Study — Confident Framing)

### 23. Have you worked with Kafka? What's your understanding of producers, consumers, topics, partitions?
**Short:** I've studied Kafka's architecture in depth as part of upskilling toward real-time data engineering — producers publish messages to topics, topics are split into partitions for parallelism, and consumers, usually organized into consumer groups, read from those partitions with offsets tracking their position.
**Detailed:** "I've put deliberate time into learning Kafka since real-time streaming is a natural extension of the Lakehouse work I already do. Producers publish events to a topic, and that topic is split into partitions — this is what allows parallel throughput, and Kafka guarantees ordering within each partition based on message key. Consumers, typically organized into consumer groups, subscribe to a topic, and Kafka divides partitions across the group so each partition is consumed by exactly one member at a time. Each consumer tracks its offset — its position within a partition — so it can resume exactly where it left off after a restart. I've worked through this hands-on with local Kafka setups and Spark Structured Streaming integration, and conceptually it maps well to the incremental watermark-based loading I already do in production — just event-driven and continuous instead of scheduled."

### 24. How would you design a real-time ingestion pipeline using Kafka + Spark Structured Streaming?
**Short:** Producers publish events to Kafka topics, Spark Structured Streaming reads from Kafka as a streaming source and processes it in micro-batches, applying the same cleansing/validation logic I use in batch, then writes to a Bronze/Silver Delta or Iceberg table with checkpointing for fault tolerance.
**Detailed:** "I'd set up Kafka topics as the ingestion layer, with source systems publishing events directly to them. Spark Structured Streaming reads from Kafka as a streaming source — Spark treats it like an unbounded, continuously-appending DataFrame — and I'd apply the same cleansing, schema validation, and dedup logic I already use in my batch pipelines, since Structured Streaming shares the same DataFrame API as batch Spark. I'd write output to a Bronze Delta or Iceberg table with checkpointing enabled, so the job can recover state after a failure without reprocessing or losing data. From there, the pattern mirrors what I already build — Silver for validated data, Gold for business-ready aggregates — just triggered continuously instead of on a schedule. I've built this exact pattern in a self-driven project to get hands-on with the mechanics before applying it in a live production setting."

### 25. Difference between batch and real-time/streaming processing.
**Short:** Batch processes bounded chunks of data on a schedule with the full dataset available upfront; streaming processes unbounded data continuously as events arrive, which is why I've focused my recent learning on Kafka and Spark Structured Streaming to build that skillset alongside my batch expertise.
**Detailed:** "My production work has been batch and incremental-batch — jobs run on a schedule, and even 'incremental' loads pull all new records since the last run in one shot. Streaming processes data continuously as it arrives, which means I need to think differently about state management, watermarking for late-arriving data, and exactly-once semantics — concerns that mostly don't apply in batch since the dataset is bounded and complete when the job runs. I've spent time learning Spark Structured Streaming specifically to understand these differences hands-on — the trade-off is streaming gives you latency in seconds instead of hours, at the cost of more operational complexity to build and monitor, and I find that trade-off is exactly why this role has real-time requirements alongside the batch Lakehouse work I already know well."

### 26. How does Kafka ensure message ordering and fault tolerance?
**Short:** Kafka guarantees ordering within a partition — same-key messages always land on the same partition and are read in write order — and fault tolerance comes from replicating each partition across multiple brokers with leader/follower failover.
**Detailed:** "Kafka guarantees ordering within a single partition — messages sharing the same key are always routed to the same partition and consumed in the order they were written. It doesn't guarantee ordering across the whole topic if there are multiple partitions, which is an important design consideration when ordering matters for a given entity. For fault tolerance, each partition is replicated across multiple brokers — one leader handles reads/writes, and followers replicate that data. If the leader broker fails, a follower is promoted automatically, so there's no data loss as long as the replication factor is configured properly. I studied this alongside how I already think about replication and durability in ADLS Gen2 and Delta/Iceberg — the underlying principle of redundancy for fault tolerance is consistent across both worlds."

### 27. Explain consumer groups and offset management.
**Short:** A consumer group is a set of consumers sharing the work of reading a topic's partitions in parallel without duplicate processing, and each consumer persists an offset — its read position — so it can resume exactly where it left off after a restart.
**Detailed:** "When multiple consumers belong to the same consumer group, Kafka divides the topic's partitions among them, so each partition is read by exactly one consumer in that group at a time — this gives parallel throughput without duplicate processing. Offsets track precisely how far each consumer has read within a partition, and Kafka persists these commits, so if a consumer crashes and restarts, it resumes from the last committed offset instead of reprocessing everything or missing data. I've worked through this in practice while setting up a local Kafka + Spark Structured Streaming pipeline — it's directly analogous to the 'last modified' watermark pattern I already use in production for incremental loads, just implemented at the individual message level and tracked automatically by Kafka rather than a custom control table."

### 28. How would you convert a batch pipeline (e.g., FinOps ADF pipeline) into a streaming pipeline?
**Short:** I'd replace the scheduled batch trigger with a Kafka source (or Event Hubs in Azure), convert the PySpark batch logic to Structured Streaming's `readStream`/`writeStream` API, and add checkpointing and stateful operations for anything that previously assumed the full dataset was available — the core transformation logic carries over largely unchanged.
**Detailed:** "The core business logic — cleansing, validation, business rules — wouldn't need a rewrite, since Structured Streaming uses the same DataFrame API as batch Spark, which is one of the things that made this transition easier for me to pick up. What changes is the source and trigger: instead of ADF kicking off a scheduled batch read from Oracle, source systems would publish change events to Kafka, or Event Hubs in Azure's ecosystem, and my Spark job would use `readStream` to consume continuously. I'd add checkpointing for fault-tolerant state recovery, and I'd need to rework anything that assumed the full dataset was available at once — like deduplication or Golden Record matching — using stateful streaming operations or windowed aggregations instead. I've practiced this exact kind of batch-to-streaming conversion as part of my self-study, converting a sample incremental pipeline into a Kafka-driven streaming version to understand the API differences firsthand."

### 29. Exactly-once vs at-least-once processing semantics.
**Short:** At-least-once guarantees no data loss but can create duplicates on retry after failure; exactly-once guarantees each record is processed and reflected in the output exactly one time, achieved through idempotent sink writes combined with checkpointed offsets.
**Detailed:** "At-least-once means that if something fails mid-processing, the system retries and reprocesses — which guarantees you never lose data, but can produce duplicates downstream if the retry re-emits records that were already partially written. Exactly-once is stronger — every record affects the output exactly once, typically achieved through idempotent sink writes combined with checkpointed offsets, so even after a failure and retry, duplicates never get committed. I already handle an equivalent concern in batch through idempotent upserts — merge logic keyed on business identifiers — so a re-run of a failed job never creates duplicates. Learning how Structured Streaming achieves the same guarantee through checkpointing and idempotent sinks was a natural extension of that existing mental model."

### 30. How would you handle late-arriving or out-of-order data?
**Short:** I'd use event-time windowing combined with watermarking — the watermark defines how long to wait for late data before finalizing a window's results — which I've implemented hands-on while learning Structured Streaming.
**Detailed:** "In Structured Streaming, you handle this with event-time windowing combined with watermarks — the watermark tells Spark how long to wait for late-arriving data before finalizing a window's aggregation and discarding anything later than that threshold. It's a deliberate trade-off between result completeness and how long you're willing to delay finalizing output. This maps directly to a problem I already solve in batch — source systems occasionally send corrected records after the original load, and I use merge/upsert logic keyed on business ID and a last-modified timestamp to reconcile those late corrections rather than treating them as new records. Working through watermarking in a hands-on Structured Streaming setup helped me see it's really the same reconciliation problem, just handled continuously instead of on a schedule."

### 31. What are checkpointing and watermarking in Structured Streaming?
**Short:** Checkpointing persists a streaming query's progress and state to reliable storage so it can recover after failure without data loss or duplication; watermarking defines a threshold for how late data can arrive before being excluded from windowed aggregations.
**Detailed:** "Checkpointing writes metadata about processed offsets and intermediate state to reliable storage — that's what lets a streaming job restart after a failure and pick up exactly where it left off, which is critical for fault tolerance in a continuously running system. Watermarking specifically addresses late data in windowed aggregations — you configure something like 'wait up to 10 minutes for late data,' and once that threshold passes for a given window, Spark finalizes and emits the result, dropping anything arriving after. I set both of these up in a hands-on Structured Streaming project reading from Kafka, which gave me practical exposure to configuring checkpoint locations and tuning watermark delay — the same class of problem I already handle in batch through reconciliation logic for late-arriving corrections."

### 32. How does your incremental loading experience relate to Kafka-based streaming?
**Short:** Both solve the same core problem — processing only what's new since the last checkpoint — my incremental loads use a watermark column and persist state between runs, which is the same underlying concept as Kafka's offset tracking, just applied continuously at the message level instead of per batch run.
**Detailed:** "The core problem is identical — knowing exactly what's 'new' since you last processed something — I've just solved it on a batch cadence in production, and now on a continuous basis through my Kafka and Structured Streaming learning. In my incremental loads, I track a high-water-mark, usually a last-modified timestamp or an incrementing ID, pull only records newer than that mark, and update it after a successful run. Kafka does the equivalent through partition offsets, tracked automatically at the individual message level, continuously rather than per batch. I also worked with a SharePoint source using a streaming read pattern in PySpark in production, which gave me an early bridge into event-driven thinking before I formalized that knowledge with dedicated Kafka and Structured Streaming study — between the two, I'm confident I can be productive on real-time pipelines quickly in this role."

## Section 4: Data Architecture & Warehousing

### 33. How do you decide between a data mart, warehouse, and data lake?
**Short:** Data lake for raw, large-scale, varied data at low cost; data warehouse for curated, structured data needing fast BI query performance; data mart for a narrower, department-specific subset of the warehouse.
**Detailed:** "I think about it based on who's consuming the data and how. If it's raw ingestion from many source systems in different formats, at large scale, it goes into the data lake — that's our Bronze/Raw layer in ADLS Gen2 or S3. Once it's cleaned and modeled for business use, structured data needing fast, reliable query performance for reporting goes into a data warehouse, like our Azure SQL Database Gold layer feeding 300+ finance reports. A data mart would be a further-scoped-down version of that warehouse for a single department or use case — I haven't built dedicated marts, but conceptually it's the same Gold-layer thinking, just narrower in scope."

### 34. Star schema vs snowflake schema.
**Short:** Star schema has a central fact table connected directly to denormalized dimension tables; snowflake schema normalizes those dimensions further into sub-tables, trading some redundancy reduction for more complex joins.
**Detailed:** "A star schema keeps dimension tables denormalized and directly linked to the fact table — simpler joins, better query performance, more storage redundancy. A snowflake schema normalizes dimensions further into related sub-tables, saving storage but requiring more joins. In my Gold layer reporting tables for FinOps, I generally favored a star-schema-like design for the finance reports — since query performance for the business teams mattered more than storage optimization, and Azure SQL Database performed better with fewer joins for that reporting workload."

### 35. How do you design architecture supporting both BI and ML workloads?
**Short:** I'd keep a clean, well-governed Gold layer for BI with aggregated, business-friendly tables, while ML teams typically consume from Silver or a feature-engineering layer with more granular, less pre-aggregated data.
**Detailed:** "BI and ML have different needs from the same underlying data. BI reporting wants clean, aggregated, business-friendly Gold tables — that's what I built for FinOps's 300+ reports. ML workloads usually need more granular, less pre-aggregated data, sometimes at the Silver layer, so data scientists can engineer their own features without losing information through premature aggregation. My approach would be to keep Silver as a well-validated but still granular layer that ML teams can consume directly, while Gold stays optimized and pre-aggregated specifically for BI — that way I'm not forcing one team's needs to compromise the other's."

### 36. What is data partitioning strategy and how did you decide partition keys?
**Short:** I partition based on the most common query filter columns — often date-based — while avoiding over-partitioning that creates too many small files.
**Detailed:** "I generally pick partition keys based on how the data is most commonly filtered downstream — in FinOps, that was often a reporting period or date column, since most of our 300+ reports filtered by time range. I balance this against partition cardinality — too granular, like partitioning by exact timestamp, creates too many small partitions and files; too coarse, and I lose the pruning benefit. With Iceberg's hidden partitioning, I had more flexibility since I could apply transforms like `days()` or `months()` without users needing to know the physical layout, which made it easier to tune partitioning without breaking downstream queries."

### 37. How do you handle Slowly Changing Dimensions (SCD Type 1/2)?
**Short:** For Type 1, I simply overwrite the old value with the new one; for Type 2, I add effective/expiry dates and insert a new row for each change, preserving history.
**Detailed:** "For dimensions where I only need the current value — like a corrected spelling of a business unit name — I use Type 1, a straightforward overwrite via merge/upsert. For dimensions where historical accuracy matters, like tracking how an account's classification changed over time for audit purposes, I use Type 2 — I add `effective_date` and `end_date` columns, mark the old record as expired, and insert a new row with the updated value as current. In eCDP's Golden Record work specifically, preserving historical lineage mattered for regulatory reasons, so Type 2-style versioning was closer to how I approached identity resolution history."

### 38. Walk me through architecting a Lakehouse from scratch for a new business domain.
**Short:** I'd start by understanding source systems and consumption patterns, then design Bronze for raw ingestion, Silver for validated/cleansed data, Gold for business-ready curated data, with governance, partitioning, and access control layered in from day one.
**Detailed:** "First, I'd map out the source systems — what format, how frequently they change, batch vs streaming — and understand who consumes the data and how, BI, ML, ad hoc analytics. ## Section 5: ETL/ELT Pipeline Design

### 40. Walk me through FinOps Dataverse pipeline end-to-end.

Incremental loading logic ensures we only process new or changed records each run, which cut execution time by 30%. The curated Gold layer loads into both Delta Lake and Azure SQL Database, where I applied Z-ordering, clustering, and file compaction, along with SQL validation — that combination cut query latency by 40% across 300+ business reports used by finance stakeholders."

### 41. How did your configuration-driven framework reduce onboarding time by 50%?
**Short:** Instead of hand-coding a new pipeline per source, I built a metadata-driven framework where adding a new source meant adding configuration — connection details, schema mapping, business rules — rather than new code.
**Detailed:** "Before this framework, onboarding a new data source likely meant writing a new ADF pipeline and PySpark notebook from scratch each time — repetitive and error-prone. ### 42. Describe your incremental loading logic.
**Short:** I track a watermark — usually a last-modified timestamp or incrementing key — store the last successfully processed value, and each run pulls only records newer than that watermark, then updates it after a successful load.
**Detailed:** "My incremental loading pattern is watermark-based. I maintain a control table or metadata store that tracks the last successfully processed value for each source — typically a last-modified timestamp or a monotonically increasing ID. Each pipeline run queries the source for records greater than that watermark, processes them through the Bronze-Silver-Gold flow, and only after a successful, validated load do I update the watermark to the new high value. This ensures if a run fails partway through, I don't lose track of what's actually been processed, and I don't risk skipping or reprocessing records. This pattern was core to reducing FinOps pipeline execution time by 30%, since we stopped reprocessing the entire dataset on every run."

### 43. How do you handle pipeline failures and retry/error-handling logic?
**Short:** I use ADF's built-in retry policies and failure paths for orchestration-level failures, and within PySpark I wrap critical transformation steps in try/except with logging, routing bad records to a quarantine location rather than failing the whole job.
**Detailed:** "At the orchestration layer, ADF pipelines have configurable retry policies on activities — for transient issues like network blips connecting to Oracle, a retry with backoff often resolves it without manual intervention. For genuine failures, I set up failure paths that trigger alerting rather than silently failing. Within PySpark transformation logic, I build in validation checks and quarantine bad records — say a record with an unexpected null in a required field — rather than letting one bad record fail the entire batch job. This was especially important in eCDP given we were processing 10M+ records daily at 99.9% availability — a single malformed record couldn't be allowed to take down the whole pipeline."

### 44. What monitoring and alerting did you set up?
**Short:** I used ADF's built-in monitoring and pipeline run history for orchestration-level visibility, combined with custom logging and row-count/data-quality checks at each layer, with alerts on failures or anomalies.
**Detailed:** "For orchestration, ADF's monitoring tab gives pipeline run history, duration, and failure reasons out of the box, and I set up alerts for failed runs so the team gets notified quickly rather than discovering issues when a business user complains about a stale report. ### 45. How do you ensure idempotency in your ETL jobs?
**Short:** I use merge/upsert logic keyed on business identifiers rather than plain inserts, so re-running a job doesn't create duplicate records.
**Detailed:** "Rather than doing a straight append/insert, I design my writes as merge operations — using Delta's or Iceberg's MERGE INTO syntax, keyed on the natural business key. That way, if a job fails partway and I re-run it, or if the same source record legitimately gets picked up twice, the merge logic updates the existing record instead of creating a duplicate. ### 46. Describe a time a pipeline failed in production — root cause and resolution.
**Short:** In eCDP, a core pipeline was running much longer than expected due to a non-partition-aligned filter causing a full table scan; I traced it through the Spark UI, fixed the filter to align with our partition column, and combined it with partition tuning to cut runtime from 4 hours to 58 minutes.
**Detailed:** "One case that stands out is a core pipeline in eCDP that was taking around 4 hours to run — well beyond what the data volume should've required. I used the Spark UI to look at stage-level timing and found one stage was scanning far more data than expected. Digging in, the filter logic wasn't aligned with how the underlying data was partitioned, so Spark couldn't prune partitions effectively and was scanning nearly the full dataset every run. I restructured the filter to align with our partition column and combined that with broader partition tuning across the pipeline. That single fix, alongside the tuning work, brought the runtime down from 4 hours to 58 minutes — a huge win for a pipeline processing 10M+ records daily."

### 47. How do you validate data quality after migration?
**Short:** I run row-count reconciliation between source and target, checksum or aggregate-value comparisons on key business metrics, and spot-check sampled records for field-level accuracy.
**Detailed:** "For our 20+ TB pharmaceutical migration to Iceberg, validation happened at multiple levels. Second, I compared aggregate values on key business metrics — sums, distinct counts on critical fields — between source and migrated data, which catches subtler issues than row counts alone. Third, I did targeted spot-checks on sampled records, especially for complex transformation logic like our Golden Record deduplication, to manually verify field-level accuracy. This combination gave us confidence for a zero-data-loss cutover on a project of that scale."

## Section 6: SQL, NoSQL & Databases

### 48. SQL query to find duplicate records based on a business key — relate to Golden Record/XREF work.
**Short:** I'd use `GROUP BY` on the business key with `HAVING COUNT(*) > 1`, or a window function like `ROW_NUMBER()` partitioned by the key to identify and rank duplicates for resolution.
**Detailed:** "A simple approach: `SELECT business_key, COUNT(*) FROM table GROUP BY business_key HAVING COUNT(*) > 1` — that flags which keys have duplicates. For actually resolving them, I'd use a window function: `ROW_NUMBER() OVER (PARTITION BY business_key ORDER BY last_updated DESC)` — this ranks duplicate records so I can keep the most recent or most complete one as the 'golden' record and mark others for merge or XREF mapping. This is essentially what I built in eCDP's Golden Record and XREF identity resolution workflows — identifying duplicate or conflicting records across source systems like Oracle, Snowflake, and Smartsheets, then establishing a single trusted record while maintaining cross-reference mappings back to the source systems."

### 49. Explain window functions with an example.
**Short:** Window functions perform calculations across a set of rows related to the current row without collapsing them into a single output row — I've used `ROW_NUMBER()`, `RANK()`, and running totals in reporting queries.
**Detailed:** "Unlike a `GROUP BY` aggregate which collapses rows, a window function computes a value across a defined 'window' of related rows while keeping each row in the output. A practical example from my reporting work: calculating a running total of transactions per business unit ordered by date — `SUM(amount) OVER (PARTITION BY business_unit ORDER BY transaction_date)`. I've also used `ROW_NUMBER()` and `RANK()` for deduplication logic, picking the latest record per key, which was a core part of my Golden Record resolution logic in eCDP."

### 50. Relational vs non-relational databases — when would you pick each?
**Short:** Relational databases like Azure SQL or Oracle fit structured data with well-defined relationships and need for ACID transactions; NoSQL fits flexible or rapidly evolving schemas, high write throughput, or document/key-value access patterns.
**Detailed:** "My production experience is with relational systems — Oracle as a source, Azure SQL Database as our curated reporting layer — which made sense because financial and pharmaceutical data has clear structure, defined relationships, and needs strong consistency guarantees for reporting accuracy. NoSQL databases would make more sense for use cases with flexible or fast-changing schemas, very high write throughput, or when the access pattern is naturally document- or key-value-based, like storing semi-structured event logs or user session data. I haven't used NoSQL hands-on in production yet, but I understand the trade-off — you often give up strict consistency and complex joins in exchange for horizontal scalability and schema flexibility."

### 51. How would you approach data modeling for a NoSQL database?
**Short:** Instead of normalizing like in relational modeling, I'd design around access patterns — denormalizing and embedding related data together to optimize for how it's queried, since joins are expensive or unavailable in most NoSQL systems.
**Detailed:** "The mental shift from relational modeling is significant — in SQL, I normalize to reduce redundancy and rely on joins to bring data together at query time. In a NoSQL document store, I'd instead model around the specific access patterns the application needs — if I know a query always needs a customer along with their recent orders, I might embed or denormalize that data together in a single document, accepting redundancy in exchange for fast, join-free reads. I haven't implemented this in production, but conceptually it's the same design-for-consumption thinking I already apply when building Gold-layer reporting tables — optimizing structure for how the data will actually be queried, not just for storage efficiency."

### 52. How do you optimize a slow SQL query?
**Short:** I check the execution plan for full table scans or missing indexes, add appropriate indexes on filter/join columns, rewrite inefficient joins or subqueries, and verify statistics are up to date.
**Detailed:** "First step is always the execution plan — I look for full table scans where an index seek should be happening, expensive sort or hash operations, or poor join order. If I see a full scan on a large table where I'm filtering on a specific column, I'd check if an index exists on that column and add one if not. I also look at whether subqueries can be rewritten as joins or CTEs for better optimizer behavior, and whether outdated statistics are causing the optimizer to pick a bad plan. In my FinOps reporting work, this kind of query tuning — alongside Z-ordering at the Delta/Iceberg layer — was part of how we drove down query latency by 40% for the business reports."

### 53. Explain your identity resolution/Golden Record logic.
**Short:** I built matching logic to identify records across systems representing the same real-world entity, merged them into a single trusted 'golden' record, and maintained an XREF mapping table linking the golden record back to each source system's original ID.
**Detailed:** "In eCDP, pharmaceutical and clinical data came in from multiple source systems — Oracle, Snowflake, REST APIs, flat files, Smartsheets — often with the same real-world entity represented differently, or with conflicting values, across systems. My identity resolution logic matched records likely representing the same entity based on key business attributes, then applied rules to resolve conflicts — for example, preferring the most recently updated or most authoritative source for a given field — to produce a single Golden Record. Alongside that, I maintained XREF tables that mapped each source system's original identifier to the corresponding Golden Record ID, so downstream consumers could always trace a curated record back to its origin. This significantly improved cross-system data consistency and reduced duplicate or conflicting records reaching downstream reporting."
